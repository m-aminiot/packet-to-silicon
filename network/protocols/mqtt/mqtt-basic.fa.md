# 📡 MQTT — بخش ۱: Basic | مفاهیم پایه و کارگاه عملی

# 🟢 سطح اول: مقدماتی (Basic) - مفاهیم پایه و معماری

در این بخش با فلسفه طراحی پروتکل MQTT، جایگاه آن در مدل شبکه و نحوه ارسال و دریافت پیام‌ها آشنا می‌شویم.

## ۱. پروتکل MQTT چیست و در کدام لایه شبکه کار می‌کند؟

پروتکل MQTT در سال ۱۹۹۹ توسط مهندسان IBM برای پایش لوله‌های نفت از طریق ارتباطات ماهواره‌ای (که پهنای باند کم و تاخیر بالایی داشتند) طراحی شد.

از نظر مدل مرجع **OSI**، پروتکل MQTT در **لایه هفتم (Application Layer - لایه کاربرد)** قرار می‌گیرد؛ یعنی دقیقاً هم‌ردیف با پروتکل‌هایی مانند HTTP، FTP و WebSocket است.

### 📊 دیاگرام جایگاه MQTT در لایه‌های شبکه (OSI & TCP/IP)

```
╭──────────────────────────────────────────────────────────────────────────╮
│ 🟩 لایه ۷ (Application Layer) ──► [ 📡 پروتکل MQTT ]                     │
│    • ساختاردهی پیام‌ها، مدیریت Topicها، سطوح QoS، Retain و Last Will      │
├──────────────────────────────────────────────────────────────────────────┤
│ 🟦 لایه ۴ (Transport Layer)   ──► [ 🔒 TCP / TLS (پورت 1883 / 8883) ]    │
│    • تضمین ترتیب بسته‌ها، اتصال پایدار، یا UDP / QUIC در نسخه‌های خاص      │
├──────────────────────────────────────────────────────────────────────────┤
│ 🟨 لایه ۳ (Network Layer)     ──► [ 🌐 IP (IPv4 / IPv6) ]                │
│    • مسیریابی (Routing) و آدرس‌دهی منطقی بسته‌ها در شبکه                   │
├──────────────────────────────────────────────────────────────────────────┤
│ 🟪 لایه ۱ و ۲ (Physical/Link) ──► [ 📶 Wi-Fi | Ethernet | 4G/5G | NB-IoT]│
│    • انتقال فیزیکی بیت‌ها بر بستر سیم یا امواج رادیویی                    │
╰──────────────────────────────────────────────────────────────────────────╯
```

### چرا به طور پیش‌فرض روی TCP کار می‌کند؟

پروتکل MQTT برای عملکرد استاندارد خود بر بستر **TCP/IP** (در لایه چهارم یا Transport) سوار می‌شود. دلایل اصلی استفاده از TCP عبارت‌اند از:

1. **اتصال‌گرا بودن (Connection-oriented):** قبل از تبادل داده، یک اتصال پایدار بین کلاینت و سرور برقرار می‌شود.
2. **تضمین ترتیب بسته‌ها (Ordered Delivery):** پکت‌ها به همان ترتیبی که ارسال شده‌اند دریافت می‌شوند.
3. **تشخیص خطا (Error Checked):** لایه TCP خراب شدن بسته‌ها در مسیر شبکه را مدیریت می‌کند.

> [!NOTE]
> **پورت‌های استاندارد MQTT:**
> * 🔓 پورت `1883`: ارتباط MQTT معمولی (بدون رمزنگاری) روی TCP
> * 🔐 پورت `8883`: ارتباط MQTT امن (بر بستر TLS/SSL) روی TCP

## ۲. معماری Client-Broker و الگوی Publish/Subscribe

برخلاف پروتکل HTTP که از معماری مستقیم **Request/Response (درخواست/پاسخ)** بین کلاینت و سرور استفاده می‌کند، MQTT بر پایه الگوی **Publish/Subscribe (انتشار/اشتراک)** و معماری **Client-Broker** کار می‌کند.

در این معماری، فرستنده و گیرنده هیچ شناخت مستقیمی از یکدیگر (مانند آدرس IP یا پورت هم) ندارند و تمام ارتباطات از طریق یک هسته مرکزی به نام **Broker (کارگزار)** مدیریت می‌شود.

### 📊 دیاگرام معماری انتشار و اشتراک (Publish / Subscribe)

```
 🟢 ناشران (Publishers)               🟠 هسته مرکزی (Broker)             🔵 مشترکین (Subscribers)
 ═══════════════════════             ═══════════════════════            ════════════════════════

╭────────────────────────╮                                             ╭────────────────────────╮
│ 🌡️ سنسور دما (Client A) │ ── Publish ──╮               ╭── ارسال ───► │ 📱 اپ موبایل (Client C) │
╰────────────────────────╯              │               │              ╰────────────────────────╯
       (Topic: home/temp)               ▼               │                     (Sub: home/#)
                               ╭─────────────────╮      │
                               │  🔄 MQTT Broker │ ─────┤
                               │ (EMQX/Mosquitto)│      │
       (Topic: home/door)               ▲               │                     (Sub: home/#)
╭────────────────────────╮              │               │              ╭────────────────────────╮
│ 🚪 سنسور درب (Client B) │ ── Publish ──╯               ╰── ارسال ───► │ 🗄️ دیتابیس (Client D)   │
╰────────────────────────╯                                             ╰────────────────────────╯
```

### اجزای اصلی این معماری:

1. **🟢 MQTT Client (کلاینت):** هر دستگاهی (از یک میکروکنترلر کوچک مثل ESP32 گرفته تا یک سرور قدرتمند لینوکسی یا اپلیکیشن موبایل) که کتابخانه MQTT را اجرا کند و به بروکر متصل شود، یک کلاینت است. هر کلاینت می‌تواند هم‌زمان هم فرستنده (**Publisher**) و هم گیرنده (**Subscriber**) باشد.
2. **🟠 MQTT Broker (بروکر):** قلب تپنده شبکه است. وظایف بروکر عبارت‌اند از:
   * پذیرش و مدیریت هزاران یا میلیون‌ها اتصال هم‌زمان کلاینت‌ها.
   * دریافت پیام‌ها از سمت Publisherها.
   * فیلتر کردن پیام‌ها بر اساس موضوع (Topic) و ارسال آن‌ها **فقط** به Subscriberهایی که متقاضی آن موضوع هستند.
   * مدیریت امنیت، احراز هویت و ذخیره وضعیت کلاینت‌ها.
3. **📤 عملیات Publish (انتشار):** زمانی که یک کلاینت پیامی را روی یک موضوع مشخص به سمت بروکر می‌فرستد.
4. **📥 عملیات Subscribe (اشتراک):** زمانی که یک کلاینت به بروکر اعلام می‌کند: «هر زمان پیامی در موضوع $X$ آمد، یک نسخه از آن را برای من هم بفرست».

### مزایای جداسازی (Decoupling) در الگوی Pub/Sub:

* **🌍 جداسازی مکانی (Space Decoupling):** فرستنده و گیرنده نیازی به دانستن آدرس IP یکدیگر ندارند.
* **⏱️ جداسازی زمانی (Time Decoupling):** فرستنده و گیرنده مجبور نیستند دقیقاً در یک لحظه آنلاین باشند (بروکر می‌تواند پیام را نگه دارد).
* **⚡ جداسازی همگام‌سازی (Synchronization Decoupling):** عملیات ارسال و دریافت به صورت غیرهمگام (Asynchronous) انجام می‌شود و برنامه کلاینت قفل (Block) نمی‌شود.

## ۳. مفهوم Topic (تاپیک) و ساختار درختی آن

در MQTT، پیام‌ها مستقیماً به آدرس کلاینت‌ها فرستاده نمی‌شوند، بلکه به آدرس‌هایی متنی به نام **Topic (موضوع)** ارسال می‌گردند. تاپیک‌ها در واقع کانال‌های مسیریابی پیام در بروکر هستند.

### ویژگی‌های Topic:

* یک رشته متنی با کدگذاری **UTF-8** است.
* ساختار سلسله‌مراتبی (درختی) دارد که سطوح آن با علامت اسلش (`/`) از هم جدا می‌شوند.
* **حساس به حروف کوچک و بزرگ (Case-Sensitive)** است؛ یعنی `home/temp` با `Home/Temp` دو تاپیک کاملاً متفاوت هستند.
* نیازی به ساختن یا تعریف قبلی ندارند! به محض اینکه کلاینتی روی یک تاپیک Publish یا Subscribe کند، آن تاپیک به صورت پویا در بروکر شکل می‌گیرد.

### 🌳 دیاگرام درختی تاپیک‌ها در یک خانه هوشمند

```
🏠 home
 ├── 🛋️ livingroom
 │    ├── 🌡️ temperature   ──►  آدرس کامل:  home/livingroom/temperature
 │    └── 💡 light         ──►  آدرس کامل:  home/livingroom/light
 │
 └── 🍳 kitchen
      ├── 🌡️ temperature   ──►  آدرس کامل:  home/kitchen/temperature
      └── 🔥 smoke         ──►  آدرس کامل:  home/kitchen/smoke
```

### کاراکترهای جایگزین (Wildcards) در هنگام Subscribe:

اگر یک کلاینت بخواهد به جای اشتراک تک‌تک تاپیک‌ها، به مجموعه‌ای از تاپیک‌ها گوش دهد، از **Wildcardها** استفاده می‌کند:

> [!IMPORTANT]
> استفاده از Wildcardها **فقط در هنگام Subscribe** مجاز است. هنگام Publish کردن، پیام باید دقیقاً به یک تاپیک مشخص ارسال شود.

#### ۱. تک‌سطحی (Single-Level Wildcard): علامت `+`
علامت `+` جایگزین **دقیقاً یک سطح** در ساختار تاپیک می‌شود.
* **مثال:** اشتراک روی `home/+/temperature`
* 🟢 **شامل می‌شود:**
  * `home/livingroom/temperature`
  * `home/kitchen/temperature`
* 🔴 **شامل نمی‌شود:**
  * `home/livingroom/light`
  * `home/floor1/kitchen/temperature` (چون دو سطح بین `home` و `temperature` وجود دارد).

#### ۲. چندسطحی (Multi-Level Wildcard): علامت `#`
علامت `#` جایگزین **صفر، یک یا تمام سطوح بعدی** می‌شود و همیشه باید در **انتهای تاپیک** قرار بگیرد.
* **مثال:** اشتراک روی `home/kitchen/#`
* 🟢 **شامل می‌شود:**
  * `home/kitchen/temperature`
  * `home/kitchen/smoke`
  * `home/kitchen/fridge/freezer/temp`

## ۴. سطوح کیفیت سرویس (QoS - Quality of Service)

یکی از قدرتمندترین ویژگی‌های MQTT، قابلیت تعیین **سطح تضمین تحویل پیام** یا همان **QoS** است. با توجه به اینکه شبکه‌های اینترنت اشیاء ممکن است ناپایدار باشند، MQTT سه سطح مختلف برای ارسال پیام ارائه می‌دهد.

| سطح QoS | نام استاندارد | تضمین تحویل | تعداد تبادل پکت | کاربرد اصلی |
| :---: | :---: | :---: | :---: | :--- |
| **🟢 QoS 0** | At Most Once | حداکثر یک‌بار (بدون تضمین) | ۱ پکت | داده‌های پرتکرار مثل دمای لحظه‌ای |
| **🟡 QoS 1** | At Least Once | حداقل یک‌بار (احتمال تکرار) | ۲ پکت | لاگ‌ها، هشدارها و وضعیت سنسورها |
| **🔵 QoS 2** | Exactly Once | دقیقاً یک‌بار (بدون تکرار) | ۴ پکت | تراکنش‌های مالی، فرامین حساس صنعتی |

> [!TIP]
> توافق QoS همیشه **بین یک کلاینت و بروکر** انجام می‌شود (نه مستقیماً از فرستنده تا گیرنده نهایی). اگر فرستنده با `QoS 2` پیامی را بفرستد اما گیرنده با `QoS 0` روی آن تاپیک Subscribe کرده باشد، پیام نهایی با `QoS 0` به گیرنده تحویل داده می‌شود (همیشه کمترین QoS در زنجیره ملاک گیرنده است).

---

### ۱. سطح 🟢 QoS 0: حداکثر یک‌بار (At Most Once) - معروف به *Fire and Forget*

در این حالت، فرستنده پیام را ارسال می‌کند و دیگر منتظر هیچ تاییدیه‌ای (Acknowledge) از سمت گیرنده نمی‌ماند و پیام را هم در حافظه خود ذخیره نمی‌کند.

```
 🟢 فرستنده (Publisher)                                    🟠 بروکر (Broker)
 ══════════════════════                                    ═════════════════
           │                                                       │
           │  1. 📤 PUBLISH (QoS = 0)                              │
           │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │
           │                                                       │ ──► تحویل به مشترکین
   [حذف فوری از حافظه]                                             │     (بدون ارسال پاسخ)
           │                                                       │
```

---

### ۲. سطح 🟡 QoS 1: حداقل یک‌بار (At Least Once)

در این سطح تضمین می‌شود که پیام **حتماً** به دست گیرنده می‌رسد، اما احتمال دارد در صورت کندی شبکه، پیام **بیش از یک‌بار (تکراری)** دریافت شود. فرستنده پیام را در بافر خود نگه می‌دارد تا تاییدیه **`PUBACK`** را دریافت کند.

```
 🟡 فرستنده (Publisher)                                    🟠 بروکر (Broker)
 ══════════════════════                                    ═════════════════
   [ذخیره پیام در بافر]                                            │
           │                                                       │
           │  1. 📤 PUBLISH (Packet ID = 10, QoS = 1)              │
           │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │
           │                                                       │ ──► پردازش و ارسال به مشترکین
           │  2. 📥 PUBACK (Packet ID = 10)                        │
           │ ◄╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌ │
           │                                                       │
   [حذف پیام از بافر]                                              │
```

---

### ۳. سطح 🔵 QoS 2: دقیقاً یک‌بار (Exactly Once)

بالاترین و امن‌ترین سطح کیفیت سرویس است. در این حالت تضمین می‌شود که پیام **بدون از دست رفتن** و **بدون هیچ‌گونه تکرار**، دقیقاً یک‌بار تحویل داده شود. این کار با یک مذاکره ۴ مرحله‌ای (**4-Way Handshake**) انجام می‌شود:

```
 🔵 فرستنده (Publisher)                                    🟠 بروکر (Broker)
 ══════════════════════                                    ═════════════════
   [ذخیره پیام + قفل ID]                                           │
           │                                                       │
           │  1. 📤 PUBLISH (Packet ID = 42, QoS = 2)              │
           │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │
           │                                                       │ [ثبت Packet ID 42]
           │  2. 📥 PUBREC (Publish Received | ID = 42)            │ [ارسال پیام به مشترکین]
           │ ◄╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌ │
           │                                                       │
   [حذف متن پیام، حفظ ID]                                          │
           │                                                       │
           │  3. 📤 PUBREL (Publish Release | ID = 42)             │
           │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │
           │                                                       │ [آزادسازی Packet ID 42]
           │  4. 📥 PUBCOMP (Publish Complete | ID = 42)           │
           │ ◄╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌ │
           │                                                       │
   [پایان کامل تراکنش ✅]                                          │
```

# 🛠️ از تئوری به عمل: کارگاه راه‌اندازی و تست عملی با Mosquitto

وقت آن رسیده است که تمام تئوری‌هایی را که تا اینجا بررسی کردیم (QoS، تاپیک‌ها، Retain، LWT و ...) به طور واقعی در محیط سیستم‌عامل تست کنیم. بروکر **Eclipse Mosquitto** به دلیل حجم بسیار کم (کمتر از چند مگابایت)، سرعت بالا و پشتیبانی از استانداردهای MQTT v3.1.1 و MQTT v5.0 بهترین ابزار برای راه‌اندازی لوکال و آزمایش‌های مهندسی است.

---

## ۱. نصب بروکر Mosquitto در سیستم‌عامل‌های مختلف

### 🐧 ۱. اوبونتو و دبیان (Ubuntu / Debian / Raspberry Pi OS)

```bash
# ۱. به‌روزرسانی مخازن
sudo apt update

# ۲. نصب سرویس بروکر
sudo apt install -y mosquitto

# ۳. فعال‌سازی و استارت خودکار سرویس با Systemd
sudo systemctl enable mosquitto
sudo systemctl start mosquitto

# ۴. بررسی وضعیت سرویس
sudo systemctl status mosquitto
```

> [!NOTE]
> در نسخه‌های جدید Mosquitto (نسخه ۲ به بعد)، به صورت پیش‌فرض برای امنیت، بروکر فقط به آدرس `localhost` (127.0.0.1) گوش می‌دهد و دسترسی ناشناس (بدون پسورد) از شبکه خارجی بسته است. اگر می‌خواهید از سیستم‌های دیگر درون شبکه به آن متصل شوید، فایل تنظیمات را باز کنید:
> ```bash
> sudo nano /etc/mosquitto/conf.d/default.conf
> ```
> این دو خط را به آن اضافه کرده و فایل را ذخیره کنید:
> ```text
> listener 1883
> allow_anonymous true
> ```
> سپس سرویس را ری‌استارت نمایید: `sudo systemctl restart mosquitto`

### 🔴 ۲. ردهت، سنت‌او‌اس و فدورا (RHEL / CentOS / Fedora)

```bash
# در Fedora:
sudo dnf install -y mosquitto

# در CentOS / RHEL (نیاز به مخزن EPEL):
sudo dnf install -y epel-release

# فعال‌سازی سرویس
sudo systemctl enable --now mosquitto
```

# (برای مک‌های با پردازنده Apple Silicon مسیر /opt/homebrew/sbin/mosquitto است)

### 🪟 ۴. سیستم‌عامل ویندوز (Windows)

برای ویندوز سه راه ساده وجود دارد:

1. **استفاده از فایل نصبی (MSI Installer):**
   * به صفحه دانلود رسمی در آدرس [mosquitto.org/download](https://mosquitto.org/download/) بروید.
   * فایل نصبی ۶۴ بیتی ویندوز (مانند `mosquitto-x.x.x-install-windows-x64.exe`) را دانلود و نصب کنید.
   * به عنوان یک Windows Service در بخش `Services.msc` ثبت شده و اجرا می‌شود.
2. **استفاده از پکیج منیجر Winget یا Chocolatey:**
   ```powershell
   # از طریق Winget:
   winget install EclipseFoundation.Mosquitto
   
   # یا از طریق Chocolatey:
   choco install mosquitto
   ```
3. مسیر پیش‌فرض فایل اجرایی معمولاً `C:\Program Files\mosquitto` است که پیشنهاد می‌شود آن را به متغیر محیطی `PATH` ویندوز اضافه کنید.

### 🐳 ۵. اجرای آنی با داکر (Docker & Docker Compose)

سریع‌ترین راه برای بالا آوردن یک محیط ایزوله و آماده:

**اجرا با یک دستور خطی:**
```bash
docker run -d \
  --name mosquitto-broker \
  -p 1883:1883 \
  -p 9001:9001 \
  eclipse-mosquitto:latest
```

**یا با استفاده از `docker-compose.yml`:**
```yaml
version: '3.8'
services:
  mqtt-broker:
    image: eclipse-mosquitto:latest
    container_name: mosquitto_server
    restart: always
    ports:
      - "1883:1883"      # پورت استاندارد MQTT
      - "9001:9001"      # پورت WebSocket
    volumes:
      - ./mosquitto.conf:/mosquitto/config/mosquitto.conf
      - mosquitto_data:/mosquitto/data
      - mosquitto_log:/mosquitto/log

volumes:
  mosquitto_data:
  mosquitto_log:
```

## ۲. نصب ابزارهای خط فرمان (mosquitto_sub و mosquitto_pub)

برای شبیه‌سازی کلاینت‌های MQTT بدون نیاز به کدنویسی، دو ابزار CLI وجود دارد:
* **`mosquitto_sub`:** کلاینتی برای مشترک شدن (Subscribe) روی تاپیک‌ها و گوش دادن به پیام‌ها.
* **`mosquitto_pub`:** کلاینتی برای انتشار (Publish) پیام به یک تاپیک مشخص.

```
 ┌──────────────────────┐                    ┌──────────────────────┐
 │   mosquitto_sub      │                    │   mosquitto_pub      │
 │  (شنونده / مشترک)    │                    │ (ارسال‌کننده پیام)   │
 └──────────┬───────────┘                    └──────────┬───────────┘
            │                                           │
            │ 1. SUBSCRIBE -t "sensors/#"               │ 2. PUBLISH -t "sensors/temp" -m "24.5"
            ▼                                           ▼
      ┌───────────────────────────────────────────────────────┐
      │               🔄 Mosquitto MQTT Broker                │
      │                  (localhost:1883)                     │
      └───────────────────────────────────────────────────────┘
            │
            │ 3. Forward Message -> "24.5"
            ▼
 ┌──────────────────────┐
 │ ترمینال mosquitto_sub│
 └──────────────────────┘
```

### روش نصب ابزارهای کلاینت:

* **🐧 در Ubuntu / Debian:**
  ```bash
  sudo apt install -y mosquitto-clients
  ```
* **🔴 در CentOS / Fedora:**
  ```bash
  sudo dnf install -y mosquitto
  # ابزارهای کلاینت همراه با بسته اصلی نصب می‌شوند
  ```
* **🍏 در macOS:**
  ```bash
  # با نصب brew install mosquitto، این ابزارها نیز نصب شده‌اند.
  ```
* **🪟 در ویندوز:**
  * در همان پوشه محل نصب `C:\Program Files\mosquitto` فایل‌های `mosquitto_sub.exe` و `mosquitto_pub.exe` به صورت آماده قرار دارند.

## ۳. تشریح سوئیچ‌ها و پارامترهای کلیدی CLI

این پارامترها در هر دو ابزار `mosquitto_sub` و `mosquitto_pub` کاربرد دارند:

| سوئیچ کوتاه | پارامتر معادل کامل | توضیح عملکرد |
| :---: | :--- | :--- |
| **`-h`** | `--host` | آدرس IP یا دامنه بروکر (پیش‌فرض: `localhost`) |
| **`-p`** | `--port` | پورت اتصال بروکر (پیش‌فرض: `1883`) |
| **`-t`** | `--topic` | تاپیک مورد نظر برای انتشار یا اشتراک (اجباری) |
| **`-m`** | `--message` | متن داده ارسالی یا Payload (مخصوص `mosquitto_pub`) |
| **`-q`** | `--qos` | سطح کیفیت سرویس: `0`، `1` یا `2` (پیش‌فرض: `0`) |
| **`-r`** | `--retain` | ارسال پیام با فلگ ماندگاری Retain (مخصوص `mosquitto_pub`) |
| **`-v`** | `--verbose` | نمایش نام تاپیک در کنار متن پیام دریافتی (مخصوص `mosquitto_sub`) |
| **`-i`** | `--id` | تعیین شناسه یکتای کلاینت (`client-id`) |
| **`-u` / `-P`**| `--username` / `--pw` | نام کاربری و کلمه عبور برای احراز هویت |
| **`-c`** | `--disable-clean-session` | غیرفعال‌سازی Clean Session (حفظ نشست پایدار) |
| **`-C`** | `--count` | دریافت تعداد مشخصی پیام و سپس خروج خودکار (مخصوص `mosquitto_sub`) |
| **`-V`** | `--protocol-version` | انتخاب نسخه پروتکل: `mqttv311` (پیش‌فرض) یا `mqttv5` |
| **`--will-topic`**| `--will-topic` | تاپیک پیام وصیت‌نامه (LWT) هنگام قطعی غیرعادی |
| **`--will-payload`**| `--will-payload`| متن پیام وصیت‌نامه کلاینت |

## ۴. سناریوهای عملی گام‌به‌گام (Hands-on Labs)

برای درک کامل، دو پنجره ترمینال را در کنار هم باز کنید.

### سناریوی ۱: اولین تست ساده (Pub/Sub محلی)

**ترمینال ۱ (شنونده):**
```bash
# گوش دادن به تاپیک خانه هوشمند روی سرور محلی
mosquitto_sub -h localhost -p 1883 -t "home/livingroom/temp" -v
```

**ترمینال ۲ (فرستنده):**
```bash
# ارسال دمای ۲۶ درجه
mosquitto_pub -h localhost -p 1883 -t "home/livingroom/temp" -m "26.0 C"
```
*نتیجه:* در ترمینال ۱ بلافاصله عبارت `home/livingroom/temp 26.0 C` چاپ می‌شود.

---

### سناریوی ۲: تست تضمین تحویل با QoS 2

در این سناریو پیام با تضمین قطعی ۴ مرحله‌ای ارسال می‌شود:

**ترمینال ۱ (Subscriber با QoS 2):**
```bash
mosquitto_sub -h localhost -t "factory/alarm" -q 2 -v
```

**ترمینال ۲ (Publisher با QoS 2 و نمایش لاگ پروتکل با سوئیچ -d):**
```bash
mosquitto_pub -h localhost -t "factory/alarm" -m "OVERHEAT_EMERGENCY" -q 2 -d
```

> [!TIP]
> با زدن سوئیچ `-d` (Debug Mode)، لاگ تبادل پکت‌ها را در خروجی می‌بینید:
> `Client ... sending PUBLISH (d0, q2, r0, m1, ...)`  
> `Client ... received PUBREC`  
> `Client ... sending PUBREL`  
> `Client ... received PUBCOMP`  
> این دقیقاً همان چرخه ۴ مرحله‌ای QoS 2 است که در بخش تئوری بررسی کردیم!

---

### سناریوی ۳: تست پیام ماندگار (Retained Message)

تفاوت پیام Retained را آزمایش می‌کنیم؛ ابتدا پیام را می‌فرستیم و **سپس** کلاینت را وصل می‌کنیم!

**مرحله اول: ارسال پیام ماندگار (قبل از اینکه کسی شنونده باشد!):**
```bash
mosquitto_pub -h localhost -t "device/status" -m "MACHINE_READY" -r
```

**مرحله دوم: باز کردن ترمینال شنونده (چند ثانیه یا چند دقیقه بعد):**
```bash
mosquitto_sub -h localhost -t "device/status" -v
```
*نتیجه شگفت‌انگیز:* به محض اجرای دستور، کلاینت آخرین وضعیت را فوراً دریافت می‌کند:
`device/status MACHINE_READY`

**مرحله سوم: پاک کردن پیام Retained از حافظه بروکر:**
```bash
# ارسال پیامی خالی با فلگ -r حافظه بروکر را ریست می‌کند
mosquitto_pub -h localhost -t "device/status" -r -m ""
```

---

### سناریوی ۴: شبیه‌سازی مرگ ناگهانی و وصیت‌نامه (LWT)

در این سناریو، یک کلاینت وصیت‌نامه تنظیم می‌کند و سپس اتصال آن را به طور غیرمحترمانه (Kill) قطع می‌کنیم تا بروکر وصیت‌نامه را اجرا کند.

**ترمینال ۱ (داشبورد مانیتورینگ وضعیت سنسور):**
```bash
mosquitto_sub -h localhost -t "nodes/sensor1/status" -v
```

**ترمینال ۲ (سنسور که با وصیت‌نامه آنلاین می‌شود):**
```bash
# اتصال سنسور به مدت نامحدود با تایمر Keep-Alive ۱۰ ثانیه‌ای
mosquitto_sub -h localhost -t "dummy/topic" \
  -i "SensorNode_01" \
  -k 10 \
  --will-topic "nodes/sensor1/status" \
  --will-payload "LOST_CONNECTION_ALARM" \
  --will-qos 1
```

**مرحله سوم (قطع ناگهانی فرآیند سنسور):**
در ترمینال ۲، با فشردن کلیدهای `Ctrl + C` یا کشتن پروسه (`kill -9`)، سوکت را بدون ارسال پکت `DISCONNECT` قطع کنید.

*نتیجه:* پس از انقضای زمان Keep-Alive بروکر، در ترمینال ۱ پیام زیر منتشر می‌شود:
`nodes/sensor1/status LOST_CONNECTION_ALARM`

---

### سناریوی ۵: انتشار و قالب‌بندی داده‌های ساختاریافته (JSON Payload)

در دنیای واقعی، داده‌های IoT به صورت رشته‌های JSON ارسال می‌شوند.

**ترمینال ۱ (مشترک شدن روی تمام سنسورهای آب‌وهوا با Wildcard):**
```bash
mosquitto_sub -h localhost -t "weather/+/telemetry" -v
```

**ترمینال ۲ (ارسال داده ساختاریافته سنسور ایستگاه ۱):**
```bash
mosquitto_pub -h localhost -t "weather/station_tehran/telemetry" -m '{
  "station_id": "THR-01",
  "temperature": 23.4,
  "humidity": 41,
  "pressure": 1013.25,
  "timestamp": 1714470000
}'
```

### سناریوی ۶: اتصال و تست روی بروکر آنلاین عمومی (بدون نیاز به نصب سرور محلی)

اگر در حال حاضر بروکری روی سیستم خود نصب ندارید، می‌توانید از بروکرهای رایگان و عمومی تست در بستر اینترنت استفاده کنید:

**شنونده روی تاپیک اختصاصی شما در بروکر عمومی EMQX:**
```bash
mosquitto_sub -h broker.emqx.io -p 1883 -t "my_unique_project_2026/#" -v
```

**ارسال به بروکر عمومی:**
```bash
mosquitto_pub -h broker.emqx.io -p 1883 -t "my_unique_project_2026/test" -m "Hello MQTT from Terminal!"
```
