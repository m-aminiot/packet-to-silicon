# 📡 MQTT — بخش ۲: Intermediate | ساختار پکت و مکانیزم‌ها

# 🟡 سطح دوم: متوسط (Intermediate) - کالبدشکافی پکت‌ها و مکانیزم‌های کنترلی

در سطح متوسط، وارد جزئیات مهندسی پروتکل می‌شویم؛ بایت‌های پکت را می‌شماریم، نحوه کارکرد MQTT روی UDP و WebSocket را بررسی می‌کنیم و با مکانیزم‌های هوشمند `Retain` و `LWT` آشنا می‌شویم.

## ۱. ساختار دقیق پکت‌های MQTT (بررسی بایت به بایت)

چرا می‌گوییم MQTT فوق‌العاده سبک است؟ در پروتکل HTTP، هدرهای متنی به راحتی بین $200$ تا $800\text{ bytes}$ حجم دارند؛ اما در MQTT، به دلیل **باینری بودن (Binary-based)** پروتکل، کوچک‌ترین پکت کنترلی فقط $2\text{ bytes}$ حجم دارد!

### 📦 دیاگرام کالبدشکافی پکت MQTT (Packet Anatomy)

```
╭─────────────────────────────────────────────────────────────────────────────╮
│ 🟦 بخش اول: Fixed Header (هدر ثابت)                                         │
│    • وضعیت: همیشه در تمام پکت‌ها وجود دارد                                  │
│    • اندازه: بین 2 تا 5 بایت (شامل نوع پکت، فلگ‌ها و طول باقی‌مانده)        │
├─────────────────────────────────────────────────────────────────────────────┤
│ 🟨 بخش دوم: Variable Header (هدر متغیر)                                     │
│    • وضعیت: بسته به نوع پکت وجود دارد                                       │
│    • اندازه: متغیر (شامل نام تاپیک و شناسه پکت ۲ بایتی در صورت QoS > 0)     │
├─────────────────────────────────────────────────────────────────────────────┤
│ 🟩 بخش سوم: Payload (بدنه اصلی داده / محتوا)                                │
│    • وضعیت: در پکت‌هایی مثل PUBLISH و CONNECT وجود دارد                     │
│    • اندازه: از 0 بایت تا سقف 256 مگابایت (JSON, Text, Binary, Protobuf)    │
╰─────────────────────────────────────────────────────────────────────────────╯
```

### الف) کالبدشکافی 🟦 Fixed Header (بین $2$ تا $5\text{ bytes}$)

هدر ثابت در **تمامی** پکت‌های MQTT وجود دارد و ساختار بیت‌های آن به شکل زیر است:

| شماره بایت | Bit 7 | Bit 6 | Bit 5 | Bit 4 | Bit 3 | Bit 2 | Bit 1 | Bit 0 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **Byte 1** | 🟦 **Packet Type** | 🟦 **Packet Type** | 🟦 **Packet Type** | 🟦 **Packet Type** | 🟧 **DUP** | 🟩 **QoS MSB** | 🟩 **QoS LSB** | 🟪 **RETAIN** |
| **Byte 2..5** | 🟨 **Continuation Bit** | 🟨 **Length** | 🟨 **Length** | 🟨 **Length** | 🟨 **Length** | 🟨 **Length** | 🟨 **Length** | 🟨 **Length** |

#### ۱. بایت اول ($1\text{ byte} = 8\text{ bits}$):
* **🟦 ۴ بیت اول (Bit 4 تا 7) - نوع پکت (Packet Type):** مشخص می‌کند این پکت چه کاری انجام می‌دهد (با ۴ بیت می‌توان $2^4 = 16$ نوع پکت تعریف کرد):
  * `1` (`0001`): `CONNECT` (درخواست اتصال کلاینت به بروکر)
  * `2` (`0010`): `CONNACK` (تاییدیه اتصال)
  * `3` (`0011`): `PUBLISH` (انتشار پیام)
  * `4` تا `7`: `PUBACK`, `PUBREC`, `PUBREL`, `PUBCOMP` (مدیریت QoS 1 و 2)
  * `8` (`1000`): `SUBSCRIBE` (درخواست اشتراک تاپیک)
  * `12` (`1100`): `PINGREQ` (تست زنده بودن ارتباط)
  * `13` (`1101`): `PINGRESP` (پاسخ به تست زنده بودن)
  * `14` (`1110`): `DISCONNECT` (قطع اتصال محترمانه)
* **۴ بیت دوم (Bit 0 تا 3) - پرچم‌ها (Flags):** (مخصوص پکت `PUBLISH`)
  * **🟧 Bit 3 (`DUP` - Duplicate):** اگر برابر `1` باشد، یعنی این پکت قبلاً ارسال شده ولی تاییدیه نگرفته و در حال ارسال مجدد است.
  * **🟩 Bit 2 & 1 (`QoS`):** دو بیت برای نمایش سطح کیفیت سرویس (`00` برای QoS 0، `01` برای QoS 1 و `10` برای QoS 2).
  * **🟪 Bit 0 (`RETAIN`):** اگر برابر `1` باشد، به بروکر می‌گوید آخرین نسخه این پیام را ذخیره کند.

#### ۲. بایت دوم تا پنجم (🟨 Remaining Length):
این فیلد نشان می‌دهد که مجموع اندازه `Variable Header` به علاوه `Payload` چند بایت است. مهندسان MQTT از یک الگوریتم هوشمندانه به نام **Variable Byte Integer** استفاده کرده‌اند:
* از هر بایت، $7\text{ bits}$ برای عدد و $1\text{ bit}$ **(بیت هشتم یا MSB)** به عنوان پرچم ادامه (Continuation Bit) استفاده می‌شود (اگر بیت هشتم `1` باشد یعنی بایت بعدی هم جزو طول پکت است).
* بنابراین، برای پیام‌های کوچک (تا $127\text{ bytes}$)، این بخش فقط $1\text{ byte}$ اشغال می‌کند!
* حداکثر فضای قابل آدرس‌دهی با $4\text{ bytes}$ برابر است با:

$$\text{Max Payload Size} = 128^4 - 1 = 268,435,455\text{ bytes} \approx 256\text{ MB}$$

| تعداد بایت‌های Remaining Length | کمترین طول قابل نمایش | بیشترین طول قابل نمایش |
| :---: | :---: | :---: |
| 🟢 $1\text{ byte}$ | $0\text{ bytes}$ | $127\text{ bytes}$ |
| 🟡 $2\text{ bytes}$ | $128\text{ bytes}$ ($128^1$) | $16,383\text{ bytes}$ ($16\text{ KB}$) |
| 🟠 $3\text{ bytes}$ | $16,384\text{ bytes}$ ($128^2$) | $2,097,151\text{ bytes}$ ($2\text{ MB}$) |
| 🔴 $4\text{ bytes}$ | $2,097,152\text{ bytes}$ ($128^3$) | $268,435,455\text{ bytes}$ ($256\text{ MB}$) |

### ب) کالبدشکافی 🟨 Variable Header
این بخش بین هدر ثابت و Payload قرار می‌گیرد و محتوای آن بسته به نوع پکت تغییر می‌کند. برای مثال در یک پکت `PUBLISH`، هدر متغیر شامل دو بخش است:
1. **طول و نام تاپیک (Topic Name):** ابتدا $2\text{ bytes}$ طول رشته تاپیک را مشخص می‌کند و سپس کاراکترهای UTF-8 تاپیک قرار می‌گیرند.
2. **شناسه پکت (Packet Identifier):** یک عدد $2\text{ bytes}$ ($16\text{ bits}$) که **فقط در صورتی که** $\text{QoS} > 0$ **باشد** (یعنی QoS 1 یا QoS 2) در پکت قرار می‌گیرد تا بروکر و کلاینت بتوانند پیام‌ها را رهگیری کنند.

### ج) کالبدشکافی 🟩 Payload (محتوای پیام)
آخرین بخش پکت است. پروتکل MQTT نسبت به محتوا کاملاً بی‌طرف (**Data-Agnostic**) است؛ یعنی شما می‌توانید متن ساده، JSON، XML، پروتکل بافر (Protobuf)، تصویر یا فایل صوتی باینری را درون Payload بگذارید. برخی پکت‌ها مثل `PINGREQ` یا `DISCONNECT` اصلاً Payload ندارند.

#### 🧮 مثال محاسبه دقیق سایز یک پکت PUBLISH:
فرض کنید می‌خواهیم مقدار `25` را روی تاپیک `a/b` با `QoS 1` ارسال کنیم:
* **🟦 Fixed Header:** $1\text{ byte}$ (Type/Flags) + $1\text{ byte}$ (Remaining Length) = $2\text{ bytes}$
* **🟨 Variable Header:** $2\text{ bytes}$ (Topic Length) + $3\text{ bytes}$ (`a/b`) + $2\text{ bytes}$ (Packet ID) = $7\text{ bytes}$
* **🟩 Payload:** $2\text{ bytes}$ (`25`) = $2\text{ bytes}$
* **✅ مجموع کل پکت:** $2 + 7 + 2 = \mathbf{11\text{ bytes}}$!

## ۲. پیاده‌سازی MQTT بر بستر UDP و نقش کلیدی QoS 2

همان‌طور که در سطح مقدماتی دیدیم، MQTT کلاسیک روی **TCP** کار می‌کند. اما در بسیاری از سناریوهای اینترنت اشیاء (مانند سنسورهای باتری‌خور، شبکه‌های ماهواره‌ای، Zigbee یا ارتباطات رادیویی کم‌مصرف)، برقراری اتصال سه‌مرحله‌ای TCP (3-Way Handshake) و نگه‌داشتن سوکت باز، مصرف باتری و سربار شبکه را به شدت بالا می‌برد.

اینجاست که پیاده‌سازی **MQTT روی UDP** (چه به صورت کاستوم/خام و چه در قالب استاندارد رسمی **MQTT-SN** یا *MQTT for Sensor Networks*) مطرح می‌شود.

### چالش بزرگ UDP چیست و چگونه با QoS 2 حل می‌شود؟

پروتکل **UDP (User Datagram Protocol)** در لایه چهارم، یک پروتکل **بدون اتصال (Connectionless)** و **غیرقابل اعتماد (Unreliable)** است؛ یعنی:
* بسته‌ها را بدون هماهنگی قبلی پرتاب می‌کند.
* هیچ تضمینی نمی‌دهد که بسته به مقصد برسد.
* ممکن است یک بسته در شبکه دو بار کپی شود یا ترتیب بسته‌ها به هم بخورد.

**💡 راهکار مهندسی (پیاده‌سازی UDP به همراه QoS 2):**
زمانی که لایه انتقال (Transport Layer) را از TCP به **UDP** تغییر می‌دهیم، بارِ «تضمین تحویل و جلوگیری از تکرار» را از دوش لایه ۴ (شبکه) برمی‌داریم و مستقیماً به **لایه ۷ (اپلیکیشن - یعنی خود منطق پکت‌های MQTT)** منتقل می‌کنیم!

### مزایای ترکیب UDP با مکانیزم QoS 2 در لایه اپلیکیشن:

1. **🔋 حذف سربار اتصال دائمی TCP:** دستگاه می‌تواند در حالت خواب عمیق (Deep Sleep) باشد، بیدار شود، بلافاصله دیتاگرام‌های UDP مربوط به چرخه `QoS 2` (`PUBLISH` $\rightarrow$ `PUBREC` $\rightarrow$ `PUBREL` $\rightarrow$ `PUBCOMP`) را تبادل کند و دوباره به خواب برود.
2. **🛡️ جلوگیری صددرصدی از تکرار یا گم‌شدن در UDP:** حتی اگر به خاطر ماهیت UDP، بسته‌ای در مسیر گم شود، تایمر داخلی کلاینت MQTT فعال شده و پکت را مجدداً ارسال می‌کند؛ و از طرفی چون بروکر `Packet ID` را تا دریافت `PUBREL` قفل کرده است، هرگز پیام تکراری به سیستم تحویل داده نمی‌شود.
3. **📉 کاهش سایز هدر لایه ۴:** هدر TCP حداقل $20\text{ bytes}$ است، در حالی که هدر UDP تنها $8\text{ bytes}$ حجم دارد.

> [!NOTE]
> در استاندارد **MQTT-SN** (که مخصوص بسترهای UDP طراحی شده)، علاوه بر `QoS 0, 1, 2`، یک سطح ویژه به نام **`QoS -1`** هم وجود دارد که کلاینت بدون نیاز به ثبت‌نام یا حتی `CONNECT` کردن، یک بسته UDP خام را به سمت بروکر شلیک می‌کند. همچنین به جای ارسال نام طولانی تاپیک، از یک **Topic ID دو بایتی** استفاده می‌شود تا حجم بسته UDP به حداقل ممکن برسد.

## ۳. کپسوله‌سازی MQTT در وب‌سوکت (MQTT over WebSockets)

فرض کنید می‌خواهید یک داشبورد مدیریتی با **React، Vue یا JavaScript** بنویسید که مستقیماً در مرورگر کاربر باز شود و داده‌های سنسورها را به صورت زنده نمایش دهد.

### مشکل کجاست؟
مرورگرهای وب (Browsers) به دلایل امنیتی (Sandboxing) اجازه ندارند یک سوکتِ خامِ TCP (Raw TCP Socket) به پورت `1883` بروکر باز کنند! مرورگرها فقط زبان `HTTP/HTTPS` و **`WebSocket (ws/wss)`** را می‌فهمند.

### راهکار: کپسوله‌سازی (Encapsulation)
برای حل این مشکل، پکت‌های باینری MQTT را دست‌نخورده برمی‌داریم و آن‌ها را درون **Payload فریم‌های WebSocket** قرار می‌دهیم (کپسوله می‌کنیم).

### 📊 دیاگرام لایه‌های کپسوله‌سازی (MQTT over WebSockets)

│  │ 🟨 لایه ۳: بسته آی‌پی (IP Packet - IPv4 / IPv6)                      │  │

│  │  │ 🟦 لایه ۴: سگمنت تی‌سی‌پی (TCP Segment - Port 8083 / 8084)    │  │  │

### مراحل دقیق برقراری ارتباط MQTT over WebSocket:

1. **🤝 مذاکره اولیه (HTTP Upgrade Handshake):**
   مرورگر یک درخواست HTTP به بروکر (معمولاً روی پورت `8083` برای `ws` یا `8084` برای `wss`) می‌فرستد و درخواست ارتقاء پروتکل به WebSocket با زیرپروتکل **`mqtt`** را می‌دهد:
   ```http
   GET /mqtt HTTP/1.1
   Host: broker.example.com:8083
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
   Sec-WebSocket-Protocol: mqtt
   Sec-WebSocket-Version: 13
   ```

2. **🔄 تایید بروکر (Switching Protocols):**
   بروکر با کد وضعیت `101 Switching Protocols` پاسخ می‌دهد و لوله ارتباطی دوطرفه WebSocket باز می‌شود.

3. **📦 ارسال فریم‌های باینری:**
   از این لحظه به بعد، کتابخانه جاوااسکریپت (مانند `MQTT.js`) پکت باینری `CONNECT` یا `PUBLISH` را می‌سازد، آن را داخل یک **WebSocket Binary Frame (`Opcode = 0x02`)** می‌گذارد و ارسال می‌کند. بروکر نیز فریم وب‌سوکت را باز کرده (Decapsulate) و پکت MQTT داخل آن را مثل یک پکت عادی پردازش می‌کند!

> [!TIP]
> **مزیت جانبی استفاده از WebSocket:** از آنجا که ترافیک WebSocket روی پورت‌های استاندارد وب (`80` و `443`) قابل انتقال است، به راحتی از فایروال‌های سخت‌گیرانه سازمانی و پروکسی‌ها (مثل Cloudflare یا Nginx Reverse Proxy) عبور می‌کند.

## ۴. پیام‌های ماندگار (Retained Messages) به همراه مثال

در حالت عادی، وقتی یک Publisher پیامی را روی تاپیکی ارسال می‌کند، بروکر آن پیام را به کسانی که **در همان لحظه** مشترک آن تاپیک هستند می‌فرستد و سپس پیام را دور می‌اندازد. اگر کلاینت جدیدی ۵ ثانیه بعد متصل شود و روی آن تاپیک Subscribe کند، هیچ پیامی دریافت نمی‌کند تا زمانی که فرستنده دوباره پیامی بفرستد!

### فلگ Retain چه کاری انجام می‌دهد؟
اگر هنگام ارسال پکت `PUBLISH`، بیت **`RETAIN = 1`** تنظیم شود، به بروکر دستور داده می‌شود:
> «این پیام را به عنوان **آخرین وضعیت معتبر (Last Known Good Value)** برای این تاپیک در حافظه خود نگه دار. هر زمان در آینده کلاینت جدیدی روی این تاپیک Subscribe کرد، **بلافاصله** این پیام را برای او ارسال کن!»

* در هر تاپیک، بروکر **فقط و فقط یک پیام Retained** (آخرین پیامِ دارای فلگ Retain) را ذخیره می‌کند.

### 💡 مثال عملی: سنسور وضعیت درب پارکینگ

```
 🚪 سنسور درب پارکینگ                     🟠 بروکر (Broker)                     📱 اپلیکیشن موبایل (جدید)
 ════════════════════                     ═════════════════                     ═════════════════════════
           │                                      │                                         │
 [ساعت 08:00 صبح]                                 │                                         │
           │ 1. PUBLISH (Retain = True)           │                                         │
           │    Topic: garage/door                │                                         │
           │    Payload: {"state": "OPEN"}        │                                         │
           │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │ 💾 ذخیره در حافظه دائمی تاپیک           │
           │                                      │                                         │
           ⋮         (گذشت ۶ ساعت...)             ⋮                                 [ساعت 14:00 بعدازظهر]
           │                                      │         2. SUBSCRIBE (garage/door)      │
           │                                      │ ◄━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │
           │                                      │                                         │
           │                                      │ 3. ارسال فوری آخرین پیام ذخیره‌شده ⚡    │
           │                                      │    Payload: {"state": "OPEN"} [Retained]│
           │                                      │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │
```

> [!IMPORTANT]
> **چگونه یک پیام Retained را از حافظه بروکر پاک کنیم؟**
> کافی است یک پکت `PUBLISH` با **Payload خالی (Zero-byte Payload)** و فلگ **`Retain = true`** روی همان تاپیک ارسال کنید. بروکر پیام قبلی را حذف خواهد کرد.

## ۵. وصیت‌نامه کلاینت (Last Will and Testament - LWT) به همراه مثال

در دنیای واقعی، دستگاه‌ها همیشه به شکل محترمانه (با ارسال پکت `DISCONNECT`) از شبکه خارج نمی‌شوند؛ ممکن است برق دستگاه قطع شود، باتری تمام شود یا کابل شبکه کشیده شود. سایر کلاینت‌ها چطور باید بفهمند که این دستگاه ناگهان مرده است؟

اینجاست که ویژگی **Last Will and Testament (به اختصار LWT یا وصیت‌نامه)** وارد عمل می‌شود.

### مکانیزم کارکرد LWT:
کلاینت در همان لحظه اول که می‌خواهد به بروکر وصل شود (درون پکت `CONNECT`)، وصیت‌نامه خود را به بروکر تحویل می‌دهد و می‌گوید:
> «ای بروکر! این تاپیک، این متن پیام، این QoS و این وضعیت Retain وصیت‌نامه من است. تا زمانی که من زنده‌ام و پکت‌های Keep-Alive می‌فرستم به آن دست نزن؛ اما اگر ارتباط من **به صورت غیرعادی (Ungracefully)** قطع شد، این وصیت‌نامه را به نمایندگی از من برای همه منتشر کن!»

### 📊 دیاگرام چرخه حیات وصیت‌نامه (Birth + Last Will)

```
 🌡️ سنسور صنعتی (Client A)                 🟠 بروکر (Broker)                 🖥️ داشبورد مانیتورینگ (Client B)
 ═════════════════════════                 ═════════════════                 ════════════════════════════════
           │                                       │                                        │
           │                                       │      1. SUBSCRIBE (sensor1/status)     │
           │                                       │ ◄━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │
           │                                       │                                        │
 ╭─────────┴───────────────────────────────────────┴────────────────────────────────────────┴─────────╮
 │ 🟢 فاز اول: اتصال اولیه و سپردن وصیت‌نامه (LWT) به بروکر                                           │
 │                                                                                                    │
 │         │ 2. CONNECT                            │                                        │         │
 │         │    • Will Topic: "sensor1/status"     │                                        │         │
 │         │    • Will Payload: "OFFLINE"          │                                        │         │
 │         │    • Will Retain: True                │                                        │         │
 │         │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │ 📝 [ثبت وصیت‌نامه در حافظه بروکر]      │         │
 │         │ ◄╌╌╌╌╌╌╌╌╌╌╌╌ CONNACK ╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌ │                                        │         │
 ╰─────────┬───────────────────────────────────────┬────────────────────────────────────────┬─────────╯
           │                                       │                                        │
 ╭─────────┴───────────────────────────────────────┴────────────────────────────────────────┴─────────╮
 │ 🔵 فاز دوم: اعلام آنلاین بودن توسط خود سنسور (Birth Message)                                        │
 │                                                                                                    │
 │         │ 3. PUBLISH ("sensor1/status" = ONLINE)│                                        │         │
 │         │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━► │ ─── PUBLISH ("ONLINE") ──────────────► │ 🟢      │
 ╰─────────┬───────────────────────────────────────┬────────────────────────────────────────┬─────────╯
           │                                       │                                        │
 ╭─────────┴───────────────────────────────────────┴────────────────────────────────────────┴─────────╮
 │ 🔴 فاز سوم: قطع ناگهانی برق سنسور و اجرای خودکار وصیت‌نامه                                          │
 │                                                                                                    │
 │    ⚡ [قطع برق!]                                │                                        │         │
 │         │ ✕ ┄┄┄┄ (قطع ارتباط و عدم ارسال پینگ)  │                                        │         │
 │                                                 │ ⏱️ [پایان مهلت تایمر Keep-Alive]       │         │
 │                                                 │ ⚠️ [تشخیص مرگ کلاینت و انتشار LWT]     │         │
 │                                                 │ ─── PUBLISH ("OFFLINE") ─────────────► │ 🔴      │
 ╰─────────────────────────────────────────────────┴────────────────────────────────────────┴─────────╯
```

> [!TIP]
> اگر کلاینت به صورت عادی و محترمانه پکت `DISCONNECT` بفرستد، بروکر وصیت‌نامه را **حذف می‌کند و منتشر نمی‌کند** (مگر در نسخه MQTT v5 که با کد خاصی درخواست شود).
