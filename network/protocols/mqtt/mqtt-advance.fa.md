# 🔴 سطح سوم: پیشرفته (Advanced) - مقیاس‌پذیری، امنیت و معماری مدرن

در این سطح، مباحثی را بررسی می‌کنیم که یک مهندس ارشد نرم‌افزار یا معمار سیستم‌های IoT برای پیاده‌سازی MQTT در مقیاس میلیونی و محیط‌های عملیاتی (Production) به آن‌ها نیاز دارد.

## ۱. مدیریت نشست‌ها (Persistent Sessions) و مکانیزم Keep-Alive

### الف) مشکل ارتباطات نیمه‌باز (Half-Open TCP Connections) و Keep-Alive
در لایه TCP، اگر کابل شبکه یک دستگاه ناگهان کشیده شود و هیچ بسته‌ای برای بستن سوکت (`FIN` یا `RST`) ارسال نشود، سیستم‌عامل سرور ممکن است تا ساعت‌ها متوجه قطع شدن کلاینت نشود (به این حالت *Half-Open Connection* می‌گویند).

پروتکل MQTT این مشکل را با تایمر **`Keep-Alive`** (که در پکت `CONNECT` بر حسب ثانیه، مثلاً $60\text{ seconds}$، تعیین می‌شود) حل می‌کند:
* اگر در طول بازه زمانی $T$ (مثلاً $60\text{s}$)، کلاینت هیچ پکت داده‌ای نفرستد، موظف است یک پکت ۲ بایتی **`PINGREQ`** به بروکر بفرستد.
* بروکر نیز با یک پکت ۲ بایتی **`PINGRESP`** پاسخ می‌دهد.
* اگر بروکر تا زمان $1.5 \times T$ (یعنی $90\text{ seconds}$) هیچ پکتی از کلاینت دریافت نکند، اتصال را مرده فرض کرده، سوکت TCP را می‌بندد و وصیت‌نامه (LWT) را اجرا می‌کند.

### ب) نشست‌های پایدار (Persistent Sessions) و فلگ `Clean Session`
وقتی یک کلاینت قطع و دوباره وصل می‌شود، آیا بروکر باید تاپیک‌هایی که کلاینت قبلاً Subscribe کرده بود را به یاد داشته باشد؟ این رفتار توسط فلگ **`Clean Session`** (در MQTT v3.1.1) یا **`Clean Start` + `Session Expiry Interval`** (در MQTT v5.0) کنترل می‌شود:

| ویژگی | 🟡 `Clean Session = true (1)` | 🟢 `Clean Session = false (0)` (نشست پایدار) |
| :--- | :--- | :--- |
| **حافظه بروکر** | با قطع ارتباط، تمام اطلاعات کلاینت پاک می‌شود. | بروکر وضعیت کلاینت را بر اساس `Client ID` نگه می‌دارد. |
| **اشتراک‌ها (Subscriptions)** | در هر بار اتصال مجدد باید دوباره `SUBSCRIBE` کند. | تمام اشتراک‌های قبلی کلاینت حفظ می‌شوند. |
| **پیام‌های زمان قطعی** | پیام‌های ارسال‌شده در زمان آفلاین بودن کلاینت از دست می‌روند. | بروکر پیام‌های `QoS 1` و `QoS 2` را در صف (Queue) نگه می‌دارد و به محض اتصال مجدد تحویل می‌دهد. |
| **نیازمندی** | می‌تواند از `Client ID` تصادفی استفاده کند. | **الزاماً** باید یک `Client ID` ثابت و یکتا داشته باشد. |

## ۲. ویژگی‌های انقلابی در نسخه MQTT v5.0

نسخه **MQTT v3.1.1** سال‌ها استاندارد اصلی صنعت بود، اما برای معماری‌های ابری مدرن و میکروسرویس‌ها محدودیت‌هایی داشت. نسخه **MQTT v5.0** با تغییرات بزرگی منتشر شد که مهم‌ترین آن‌ها عبارت‌اند از:

### ۱. اشتراک‌های اشتراکی (Shared Subscriptions) - توزیع بار (Load Balancing)
در MQTT v3.1.1، اگر شما ۳ میکروسرویس پردازشگر دیتا داشته باشید که همگی روی تاپیک `sensors/#` مشترک شوند، هر پیام به **هر ۳ سرویس** ارسال می‌شود (تکرار پردازش!).
در **MQTT v5.0** با استفاده از سینتکس `$share/{GroupName}/{Topic}` می‌توان بین مصرف‌کنندگان **Load Balancing** انجام داد:

```
                                                          ╭─── ⚙️ گروه اشتراکی: $share/workers/sensors/# ───╮
                                                          │                                                 │
 📡 سنسورها (Publishers)          🟠 MQTT v5 Broker       │    ╭──────────────────────╮                     │
 ═══════════════════════          ═════════════════       │ ╭─►│ 🟢 Worker Service 1  │ (دریافت فقط Msg 1)  │
                                                          │ │  ╰──────────────────────╯                     │
   [Msg 1] 🟢 ──╮                 ╭───────────────╮       │ │  ╭──────────────────────╮                     │
   [Msg 2] 🔵 ──┼── Publish ────► │ توزیع چرخشی   │ ──────┼─┼─►│ 🔵 Worker Service 2  │ (دریافت فقط Msg 2)  │
   [Msg 3] 🟠 ──╯                 │ (Round-Robin) │       │ │  ╰──────────────────────╯                     │
                                  ╰───────────────╯       │ │  ╭──────────────────────╮                     │
                                                          │ ╰─►│ 🟠 Worker Service 3  │ (دریافت فقط Msg 3)  │
                                                          │    ╰──────────────────────╯                     │
                                                          ╰─────────────────────────────────────────────────╯
```

### ۲. نام مستعار تاپیک (Topic Alias)
اگر یک سنسور مدام روی تاپیک طولانی `company/factory_1/hall_B/machine_42/vibration/axis_x` پیام بفرستد، در هر پکت $52\text{ bytes}$ فقط صرف ارسال رشته تاپیک می‌شود! در MQTT v5، کلاینت در اولین پکت اعلام می‌کند که `Topic Alias = 1` معادل این تاپیک طولانی است و در پکت‌های بعدی، رشته تاپیک را خالی می‌فرستد و فقط عدد `1` را در هدر می‌گذارد (کاهش چشمگیر مصرف ترافیک).

### ۳. زمان انقضای پیام (Message Expiry Interval)
می‌توان برای هر پکت یک تایمر عمر (TTL) بر حسب ثانیه تعیین کرد. اگر کلاینت گیرنده آفلاین باشد و تا قبل از پایان این زمان آنلاین نشود، بروکر پیام منقضی‌شده را دور می‌اندازد تا صف حافظه پر نشود و داده بیات تحویل داده نشود.

### ۴. ویژگی‌های کاربر (User Properties) و الگوی Request/Response
* **User Properties:** امکان افزودن هدرهای دلخواه به صورت کلید-مقدار (`Key-Value`) به هدر پکت MQTT (مشابه هدرهای HTTP) بدون دستکاری Payload اصلی.
* **Response Topic & Correlation Data:** پشتیبانی بومی از الگوی درخواست/پاسخ (Request/Response) بر بستر ناهمگام MQTT.

## ۳. امنیت در سطح سازمانی (TLS, mTLS, ACL)

پروتکل MQTT به خودی خود هیچ رمزنگاری روی داده‌ها اعمال نمی‌کند و نام کاربری و رمز عبور در پکت `CONNECT` به صورت متن ساده (Plaintext) ارسال می‌شوند. برای امن‌سازی در محیط عملیاتی، یک معماری سه‌لایه اجرا می‌شود:

```
╭─────────────────────────────────────────────────────────────────────────────╮
│ 🛡️ لایه ۱: امنیت کانال انتقال (TLS 1.3 / mTLS روی پورت 8883)               │
│    • رمزنگاری سرتاسری ترافیک + احراز هویت دوطرفه با گواهی دیجیتال X.509     │
├─────────────────────────────────────────────────────────────────────────────┤
│ 🔑 لایه ۲: احراز هویت کلاینت (Authentication)                               │
│    • اعتبارسنجی هویت با توکن‌های JWT، OAuth 2.0 یا گواهی سخت‌افزاری (TPM)   │
├─────────────────────────────────────────────────────────────────────────────┤
│ 🚧 لایه ۳: کنترل دسترسی تاپیک‌ها (Authorization / ACL)                      │
│    • محدودسازی دقیق مجوزهای Publish و Subscribe برای هر Client ID           │
╰─────────────────────────────────────────────────────────────────────────────╯
```

### نمونه قوانین ACL (Access Control List) در بروکر:
صرفاً متصل شدن به بروکر نباید به کلاینت اجازه دهد به همه تاپیک‌ها دسترسی داشته باشد! قوانین **ACL** در بروکر تعریف می‌شوند تا هر کلاینت فقط به فضای نام (Namespace) خودش دسترسی داشته باشد:

```ini
# 🟢 کلاینت فقط اجازه دارد روی تاپیک اختصاصی خودش Publish کند:
ALLOW publish client_id="${clientid}" topic="devices/${clientid}/telemetry"

# 🔴 کلاینت اجازه ندارد روی تاپیک `#` (کل پیام‌های بروکر) Subscribe کند:
DENY subscribe topic="#"
```

## ۴. کلاسترینگ (Clustering)، مقیاس‌پذیری و مقایسه بروکرها

وقتی تعداد دستگاه‌های متصل از چند ده هزار به **چند میلیون اتصال هم‌زمان** می‌رسد، یک سرور منفرد (Single Node) به دلیل محدودیت پورت‌های شبکه، حافظه RAM و پردازنده پاسخگو نخواهد بود و تبدیل به نقطه شکست واحد (**SPOF - Single Point of Failure**) می‌شود.

### الف) معماری کلاسترینگ (Broker Clustering)
در یک کلاستر MQTT، چندین نود بروکر پشت یک **Load Balancer** (مانند HAProxy یا Envoy) قرار می‌گیرند و از طریق یک شبکه داخلی پرسرعت، جدول مسیریابی تاپیک‌ها (Topic Trie) و وضعیت نشست‌ها را با هم به اشتراک می‌گذارند.

```
     📱 میلیون‌ها کلاینت IoT             ⚖️ توزیع‌کننده بار                 🟠 کلاستر بروکر (EMQX / HiveMQ)
 ═══════════════════════════════      ═════════════════════          ═══════════════════════════════════════════

 ╭──────────────╮                                                    ╭─────────────────────────────────────────╮
 │ 📡 Client 1  │ ───╮                                          ╭──► │ 🟢 Broker Node 1                        │ ──╮
 ╰──────────────╯    │                ╭───────────────────╮     │    ╰────────────────────▲────────────────────╯   │
 ╭──────────────╮    ├── TLS (8883) ─►│   Load Balancer   │ ────┤                         │ همگام‌سازی جدول تاپیک   │
 │ 🚗 Client 2  │ ───┤                │ (HAProxy / Envoy) │     │    ╭────────────────────▼────────────────────╮   ├──► 🗄️ Kafka / DB
 ╰──────────────╯    │                ╰───────────────────╯     ├──► │ 🟢 Broker Node 2                        │ ──┤
 ╭──────────────╮    │                                          │    ╰────────────────────▲────────────────────╯   │
 │ 🏭 Client N  │ ───╯                                          │                         │ (Mesh Clustering)      │
 ╰──────────────╯                                               ╰──► ╭────────────────────▼────────────────────╮   │
                                                                     │ 🟢 Broker Node 3                        │ ──╯
                                                                     ╰─────────────────────────────────────────╯
```

### ب) مقایسه برترین بروکرهای MQTT در بازار

| نام بروکر | زبان توسعه | پشتیبانی از کلاسترینگ بومی | حداکثر اتصال هم‌زمان (در هر نود) | مناسب برای... |
| :--- | :---: | :---: | :---: | :--- |
| **Eclipse Mosquitto** | C | 🔴 ندارد (فقط Bridging) | $\sim 50\text{K} - 100\text{K}$ | پروژه‌های کوچک، لبه شبکه (Edge)، Raspberry Pi و تست. |
| **EMQX** | Erlang/OTP | 🟢 دارد (فوق‌العاده قوی) | $+1,000,000$ تا $5\text{M}$ | سیستم‌های کلان (Enterprise)، اتصال میلیونی، دارای Rule Engine داخلی قوی. |
| **HiveMQ** | Java | 🟢 دارد | $+1,000,000$ | سیستم‌های بانکی و صنعتی با پایداری و پشتیبانی تجاری بالا. |
| **NanoMQ** | C (Async) | 🟡 دارد (Bridging/QUIC) | $\sim 500\text{K}$ | گیت‌وی‌های لبه شبکه (Edge Computing) با مصرف منابع بسیار پایین و پشتیبانی از QUIC. |
| **VerneMQ** | Erlang/OTP | 🟢 دارد | $+500\text{K}$ | پروژه‌های متن‌باز مقیاس‌پذیر. |

## ۵. نسل آینده: MQTT over QUIC

همان‌طور که در بخش‌های قبلی بررسی کردیم، TCP پایه‌گذار ارتباطات پایدار در اینترنت است، اما در شبکه‌های موبایل امروزی (4G/5G) و خودروهای متصل (Connected Cars) چالش‌های جدی دارد.

مهندسان در حال مهاجرت به معماری مدرن **MQTT over QUIC** هستند (که توسط بروکرهایی مثل EMQX و NanoMQ پیشگام شده است). پروتکل **QUIC** (که زیربنای `HTTP/3` نیز هست) پروتکلی است که توسط گوگل بر بستر **UDP** طراحی شده است.

### 📊 مقایسه اتصال کلاسیک (TCP + TLS) با نسل جدید (MQTT over QUIC)

```
 🔴 روش سنتی: MQTT over TCP + TLS                           🟢 روش مدرن: MQTT over QUIC (بر بستر UDP)
 ════════════════════════════════                           ═════════════════════════════════════════
 کلاینت                        بروکر                        کلاینت                             بروکر
   │ ─── 1. TCP SYN ───────────► │                            │                                  │
   │ ◄── 2. TCP SYN-ACK ──────── │                            │ ─── 1. QUIC Handshake + TLS 1.3 ►│
   │ ─── 3. TCP ACK ───────────► │                            │ ◄── 2. QUIC Handshake Complete ──│
   │ ─── 4. TLS ClientHello ───► │                            │ ─── 3. MQTT CONNECT / PUBLISH ──►│
   │ ◄── 5. TLS ServerHello ──── │                            │                                  │
   │ ─── 6. TLS Key Exchange ──► │                            │ ⚡ برقراری اتصال در 1-RTT (یا 0-RTT)
   │ ─── 7. MQTT CONNECT ──────► │                            │ ⚡ بدون قطعی هنگام تغییر IP (واسه خودرو/موبایل)
```

### چرا MQTT over QUIC آینده اینترنت اشیاء است؟

1. **⚡ برقراری اتصال فوق‌سریع ($0\text{-RTT}$ و $1\text{-RTT}$):**
   در TCP + TLS کلاسیک، ابتدا باید ۳ مرحله Handshake برای TCP و سپس چند مرحله برای TLS انجام شود. در QUIC، رمزنگاری **TLS 1.3** در دل پروتکل ادغام شده و اتصال در $1\text{-RTT}$ (یا در اتصالات بعدی در $0\text{-RTT}$، یعنی ارسال داده در همان اولین بسته!) برقرار می‌شود.
2. **🔀 رفع مشکل Head-of-Line (HoL) Blocking:**
   در TCP، اگر یک پکت در شبکه گم شود، سیستم‌عامل تمام پکت‌های بعدی را در بافر نگه می‌دارد تا پکت گم‌شده دوباره برسد. QUIC از **چندجریانی (Multiplexing Streams)** روی UDP استفاده می‌کند؛ بنابراین گم شدن پکت یک تاپیک، پردازش سایر تاپیک‌ها را متوقف نمی‌کند.
3. **🚗 مهاجرت یکپارچه اتصال (Connection Migration):**
   وقتی یک خودروی هوشمند یا موبایل از وای‌فای خانه خارج شده و به شبکه 5G متصل می‌شود، آدرس IP آن تغییر می‌کند. در TCP، سوکت قطع شده و کلاینت باید دوباره `CONNECT` و `SUBSCRIBE` کند؛ اما در **MQTT over QUIC**، اتصال بر اساس یک `Connection ID` مستقل از IP حفظ می‌شود و بدون قطع شدن جلسه MQTT، ارتباط ادامه می‌یابد!
